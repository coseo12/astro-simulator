#### 1-C. 카메라 tween 중 사용자 입력 — 런타임 실측

시간 정지 (`?speed=0`), 페이지 안 `requestAnimationFrame` 표본으로 `focusOn` 직후 N 번째 프레임에 캔버스 이벤트를 주입했다. 기준은 같은 이동을 입력 없이 한 값.

| 경우 | 주입 시각 | 결과 (최종 상태) | 판정 |
| --- | --- | --- | --- |
| earth → mars, 입력 없음 (기준) | — | `r = 35.8` · tween 종료 308 ms | — |
| earth → mars, 휠 줌아웃 5틱 (`deltaY 240`) | 41 ms | `r = 36.7` (기준 대비 +2.5 %) | radius tween 이 휠을 **거의 전부 덮어쓴다** |
| earth → mars, 드래그 300 px | 45 ms | `alpha` −3.298 → −3.864 (드래그 반영 유지) | 시점 방향 없는 포커스는 `alpha` · `beta` 를 보간하지 않아 드래그가 **산다** |
| earth → moon `facing-parent`, 입력 없음 (기준) | — | `r 181411.9` · `alpha −6.159` · `beta 0.558` | — |
| 같은 이동 + 드래그 | 99 ms | 기준과 **유효숫자 4자리까지 동일** | 시점 방향 tween 이 드래그를 **완전히 덮어쓴다** |
| 같은 이동 + 휠 | 127 ms | 기준과 동일 | 완전히 덮어쓴다 |
| earth → mars 중 jupiter 포커스 | 48 ms | 선택 = jupiter, tween 재시작 (종료 370 ms) | 나중 명령이 이긴다 |
| 정착 후 휠 줌아웃 10틱 | 정착 후 | `r` 36.4 → 127.0, 선택 mars **유지** | 정착 후 줌은 포커스를 깨지 않는다 |
| 정착 후 드래그 (moon) | 정착 후 | `alpha` 변경, 선택 moon **유지** | 궤도 회전도 포커스를 깨지 않는다 |
| 캔버스 포커스 + `Esc` | 정착 후 | 선택 `null` · `freeFlyMode = true` | **포커스를 깨는 유일한 키** (`focus-quick-buttons.tsx`) |
| 캔버스 포커스 + `ArrowRight` 500 ms | 정착 후 | `alpha` +0.528 rad, 선택 유지 | 화살표는 **카메라 회전** (Babylon 키보드 입력) |
| 캔버스 포커스 + `Space` | — | `timeScale` 86400 그대로 | Space 전역 바인딩 없음 |

결론 3가지:

1. **입력이 tween 과 겹치는 창은 300 ms 이고 그 안에서는 tween 이 이긴다.** 그 밖의 줌 · 회전은 포커스(선택)를 깨지 않는다. 즉 「사용자 조작 ↔ 투어 장면」 충돌은 카메라 층이 아니라 **선택 · 시각 · 표시 · 자유 비행 같은 store 상태 층**에서만 생긴다.
2. 투어 단계에서 `focusOn` 직후 `setCameraRadius` 를 보내면 같은 기전으로 덮어써진다 — 단계 필드에 줌 배율을 넣으려면 tween 종료 대기가 필요하다. v1 은 넣지 않는다 (§비-범위).
3. §3.3 의 `←/→` 키는 캔버스 포커스 상태에서 이미 카메라 회전이고 스크러버도 화살표를 쓴다 — **전역 바인딩하면 충돌한다** (결정 E7).

#### 1-D. #1113 (자유 비행 상태기계 추출) 과의 관계

#1113 재평가 (2026-09-09) 의 결론은 「유예 유지」 다 — 상태기계가 `sim-canvas.tsx` 클로저 로컬이라 직접 단위 테스트가 원리적으로 불가하고, 가드 7종이 회귀를 잡고 있다. 해제 조건 3 은 「다른 작업이 이 이슈를 **선행 조건으로 요구**할 때」 다.

본 설계는 **선행 조건으로 요구하지 않는다.** 근거는 1-C 실측이다 — 투어가 필요로 하는 카메라 전이 (포커스 · 개요 · 시점 방향) 는 전부 기존 명령으로 이미 도달 가능하고, 새 전이가 없다. 투어는 자유 비행에 **들어가지 않는다**. 충돌은 store 층의 이탈 감지 (결정 E3 · 순수 함수, 단위 테스트 가능) 로 다룬다. 즉 상태기계를 넓히지 않으므로 테스트 불가 영역도 넓히지 않는다.

**#1113 해제 조건 3 이 발동하는 경계**: 투어 단계가 **연속 카메라 연출** (예: 토성 주위를 10 초 동안 도는 궤도 비행 · 경로 비행) 을 요구하는 순간이다. 그것은 명령 1회가 아니라 프레임마다 카메라를 소유하는 새 상태이고, 클로저 상태기계와 경합한다. 그때는 #1113 추출이 선행이다 (§결과 · 재검토 조건 1).

#### 1-E. 375 폭 상단 바 — 교육 탭 활성화 비용

`mode-switcher.tsx` 는 `max-sm` 에서 비활성 모드를 숨긴다 (#1281 — 좌측 그룹이 가용폭을 넘겨 우측 그룹을 0 px 로 만들던 결함). 교육을 활성화하면 그 숨김이 풀린다.

- 실측 (375 × 812): 좌측 그룹 폭 **293 px → 330 px** (교육 버튼 35 px + 간격). 모드 전환기 78 → 115 px.
- `top-bar.tsx` 의 가용폭 = 375 − `px-3` × 2 = **351 px**. 좌측 330 + 간격 8 + 「⋯」 버튼 `min-w-7` 28 = **366 px > 351 px** — 15 px 넘친다. 좌측은 `shrink-0` 라 「⋯」 가 밀려 잘린다 (#1281 과 같은 결함 클래스).

⇒ 교육 탭 활성화는 **375 상단 바 재배치를 동반해야 한다** (Q5).

#### 1-F. 투어 후보의 장면 성립 여부

- **일식** — `time-events.json` 에 `solar-eclipse` 2024-04-08 이 JD `2460409.2479` (개기, 장면 모델값 — 실제 최대식 18:17 UT 대비 #1354 정밀도 범위) 로 있다. 사건 종류 정의 (`event-kinds.ts`) 가 이미 포커스 = 지구 · `facing-parent` · 거리 자 지구를 갖는다. 월식 비교용 2025-03-14 개기 월식 JD `2460748.7964` 도 있다. ⇒ **기존 사건 선택과 같은 장면이 그대로 선다.** 단계는 JD 를 하드코딩하지 않고 사건 id (`solar-eclipse:2024-04-08`) 로 참조한다 (사건 모델이 바뀌면 단계도 따라간다).
- **별자리** — 실 GPU 실측. 지구 포커스 + `facing-parent` (카메라가 지구의 태양 쪽 = 지구 뒤 배경이 한밤의 하늘) + 별자리 켬:

  | 시각 | 화면 중심에 가까운 별자리 라벨 (중심까지 px, 1280 × 800) |
  | --- | --- |
  | 2024-12-21 동지 (JD 2460665.889) | 오리온 235 · 마차부 280 · 황소 340 · 페르세우스 406 |
  | 2024-06-20 하지 (JD 2460482.369) | 방패 180 · 궁수 214 · 남쪽왕관 301 |

  ⇒ 「계절마다 한밤의 별자리가 다르다」 장면이 **기존 시점 하나로 선다** (겨울 = 오리온, 여름 = 궁수). 새 core 코드 0. 궤도선이 화면을 가로지르므로 이 단계는 궤도선을 끈다.
- **계절** — 「하지엔 북반구가, 동지엔 남반구가 태양을 향한다」 를 보이려면 원반 중심이 태양 직하점인 시점 (태양에서 정확히 본 지구) 이 필요하다. 같은 `facing-parent` 는 거리 자 선 관통을 피하려고 카메라 위 (장면 +Y) 쪽 15° 기울기 상수 (`FOCUS_VIEW_TILT_RAD`, #1360) 를 더하므로 원반 중심이 직하점에서 벗어나고, 그 벗어남이 하지 · 동지에 대칭이라는 보장이 없다 (장면 +Y 와 황도 북극의 관계에 따라 다르다 — **미실측**, PR3 에서 원반 중심 위도로 잰다). 이 투어에는 기울기 없는 시점 (`from-sun`) 이 필요하다 — **시점 종류 1개 추가** (core 타입 + `sim-canvas` `consumeFocusView` 분기). Q1 · Q8. → **PR3 실측**: 원반 중심 위도는 하지 +23.439° · 동지 −23.439° · 추분 +0.154° 이고, 장면 위 방향 (+Y) 이 황도면 안이라 화면 위 방향을 따로 정해야 했다 ([§Amendment 2](#amendment-2-2026-10-23--pr3-concrete-prediction-pr3-반증--from-sun-화면-위-방향)).
- **태양계 한 바퀴** — 포커스 · 개요 · 표시 토글 · 배속만 쓴다. 새 코드 0.

## 결정 (사용자 결정 — 전부 권고안)

### 엔진

- **E1. 투어 데이터 = TS 선언.** `apps/web/src/lib/tours/` — `types.ts` (`TourDef` · `TourStep`) · 투어별 파일 · `index.ts` (목록). 교육 탭 진입 시 dynamic import 는 PR1 에서 번들 실측 후 판단 (20 KB 미만이면 정적).
- **E2. 진행 = 단계별 「다음」 + 단계 안 배속 연출 (축 E2 (c)).** 자동 진행 타이머 없음.
- **E4. 카메라 제어권 = 투어 컨트롤러가 기존 명령만 보낸다.** 자유 비행 상태기계 · `camera-controller.ts` · `sim-canvas` 포커스 동기를 **바꾸지 않는다**. 투어 단계는 자유 비행에 들어가지 않는다.
- **단계 형식** (요지 — 필드명은 developer 재량, 의미는 계약):

  ```text

    id         안정 id (테스트 · 문안 참조용. URL step 은 1-based 인덱스)
    title      단계 제목
    body       설명 2~4 문장 (375 에서 접지 않고 읽히는 길이 — DoD E11)

    time?      { julianDate } | { eventId, offsetHours? } | 생략 = 유지
  ```

  1. 표시 토글 (store setter + core 명령, URL 미기록 — E6)
  2. `jumpToJulianDate`
  3. `setFocusViewRequest` — 시점이 있으면 요청, **없으면 `null`** (앞 단계의 미소비 요청이 뒤늦게 새 포커스에 적용되지 않게 — §교차검증 합의 2)
  4. `focusOn` / `resetCamera`
  5. `setTimeScale`
  6. `setRulerAnchor`
- **순수 함수 2개로 분리** — `planTourStep(step, snapshot) → { 명령 · 액션 목록, plannedState }` 와 `detectTourDrift(plannedState, storeState) → 이탈 축 목록`. 사건 id → JD 해석은 `planTourStep` 한 곳에서만 하고 결과를 `plannedState` 로 넘긴다 (§교차검증 합의 4). 둘 다 단위 테스트 대상이고, 컴포넌트는 실행 · 구독만 한다.

T2 1→2 · T4 2→3 처럼 재구도가 필요한 전이에는 `view` 를 둔다.

### 사용자 조작 (E3)

- **자유 허용 + 이탈 감지.** 캔버스 줌 · 회전은 막지도 감지하지도 않는다 (1-C — 장면을 깨지 않는다).
- **이탈 축** — 단계가 맞춘 값과 store 를 비교한다:
  - `selectedBodyId` ≠ 단계 포커스 (다른 천체 선택 · `Esc` 자유 비행 · 개요 복귀 포함)
  - 단계 `timeScale === 0` 일 때 `|julianDate − 단계 시각| > 1e-6` 일 또는 `timeScale ≠ 0` (스크러버 · 재생 · 사건 선택). 같은 허용 오차를 DoD E2 와 공유한다 (§교차검증 합의 5)
  - 단계 `timeScale ≠ 0` 일 때 `timeScale` 변경, 그리고 단계가 시각을 지정했으면 `julianDate` 가 `[시작 시각, 시작 시각 + window]` 밖 (§교차검증 이견 수용 1 — 재생 중 스크러버 점프 과소 판정 차단). 시각을 지정하지 않은 재생 단계 (T1-7) 는 시각을 보지 않는다
  - `window` 끝에 도달하면 컨트롤러가 `setTimeScale(0)` 로 멈춘다 — 단계 진행은 아니다 (결정 E2 — 자동 진행 타이머 없음 유지). 이 정지는 이탈로 세지 않는다 (`plannedState` 를 정지 상태로 갱신)
  - 단계가 지정한 표시 토글 값 변경
  - `freeFlyMode === true`
- **이탈 시** — 투어는 같은 단계에 머물고 카드에 한 줄 안내 + 「이 장면으로 돌아가기」 (단계 재적용) 를 띄운다. 「다음」 · 「이전」 은 그대로 동작한다 (다음 단계 적용이 곧 복귀다). 투어를 끝내지 않는다.
- **적용 중 판정 보류** — 단계 명령 묶음을 보내는 동안은 이탈을 판정하지 않는다 (`applying` 플래그 — 묶음 중간의 store 상태가 이탈로 깜빡이지 않게, §교차검증 합의 6). 묶음이 끝난 뒤 첫 판정부터 유효하다. ⚠️ core 의 `focusOn` → `bodySelected` → store 가 묶음 안에서 동기로 끝나는지는 **미실측** — PR1 단위 · 실브라우저에서 확인하고, 비동기면 「`plannedState` 최초 도달까지 보류」 로 바꾼다.
- **모드 전환** (관찰 · 연구로) 은 투어 종료다.

### 시작 · 종료 · 복원 (Q7)

- 투어 시작 시 **표시 토글 의도 12종 스냅샷**. 종료 (종료 버튼 · 마지막 단계 「완료」 · 모드 전환 · 카드 `Esc`) 시 그 스냅샷으로 되돌린다 — store + core 명령 + **표시 URL 키** (`serializeDisplayToggle` 로 스냅샷 의도를 다시 쓴다). 투어 자신은 표시 URL 을 쓰지 않지만 투어 중 사용자가 표시 패널을 누르면 `useDisplayToggle` 이 URL 을 쓰므로, store 만 되돌리면 URL 과 화면이 어긋난다 (§교차검증 합의 3).
- 스냅샷 시점 = 투어가 시작되는 순간의 store 의도. 공유 링크 직접 진입 (`?tour=`) 이면 URL 표시 키가 이미 store 에 반영된 뒤다 (sim-canvas 가 mount 시 파싱 — 아래 URL 절의 가용성 대기와 같은 시점).
- 카메라 · 시각 · 배속은 **되돌리지 않는다** — 투어가 끝난 장면에서 바로 둘러볼 수 있게 한다.
- 교육 모드 진입만으로는 장면을 바꾸지 않는다 — 카드에 투어 목록만 뜬다.

### URL (E6)

- `?tour=<id>&step=<n>` (1-based, `history: 'replace'`). 로드 시 유효하면 그 단계를 적용 (단계가 `t` · `focus` · `speed` · `ruler` 의 정본). 무효 id · 범위 밖 step 은 키 제거 + dev 경고 (`?focus=` #418 처분).
- **초기 적용 진입점은 `UrlSync` 의 1회 초기 effect 하나** (§교차검증 합의 1) — `?tour` 가 유효하면 같은 effect 안에서 `?t` · `?focus` · `?speed` · `?ruler` 적용을 건너뛰고 투어 단계 적용으로 넘긴다. 별도 컴포넌트 effect 두 개가 같은 축에 명령을 두 번 보내는 순서 경합을 만들지 않는다. 적용 후 `UrlSync` 의 store → URL effect 가 `t` · `focus` · `ruler` 를 단계 값으로 다시 쓰는 것은 정상이다 (단계가 정본).
- **가용성 대기** (Claude 고유 발견 2) — 표시 토글 set 경로는 `displayCapabilities === null` (장면 미준비) 이면 no-op 이다 (`useDisplayToggle` 과 같은 `disabledReason`). `UrlSync` 가 그보다 먼저 돌 수 있으므로 (#419 — `UrlSync` 는 core 준비 후 렌더, 가용성은 sim-canvas 가 핸들러 등록 자리에서 set) 초기 단계 적용은 `displayCapabilities !== null` 을 1회 기다린 뒤 보낸다. 두 시점의 실제 선후는 **미실측** — PR1 에서 확인.
- **온보딩 모달 (#737)** — 유효한 `?tour=` 로 진입한 첫 방문이면 온보딩 자동 표시를 하지 않는다 (투어 카드 포커스와 모달 포커스 트랩 · `Esc` 의 경합 회피, §교차검증 합의 7). 「조작 가이드」 버튼으로는 언제든 연다.
- `?tour=` 가 있으면 `?mode=education` 을 함의한다 (모드 키가 없어도 교육 모드로 진입).
- 투어의 표시 토글 변경은 표시 URL 키를 **쓰지 않는다** (임시 상태 — 종료 시 스냅샷 복원). `useDisplayToggle` 은 그대로 두고, 투어 전용 「지정값 set」 경로를 같은 표 (`display-toggles.ts`) 위에 둔다 (가용성 검사 `disabledReason` 동일 적용 — 소프트웨어 렌더에서 별자리 단계는 「이 환경에서는 별을 그릴 수 없습니다」 안내를 카드에 낸다).

### 카드 UI (E5)

- **데스크톱 (≥ 640 px)** — 하단 중앙, 타임바 위 (`bottom` 은 타임바 상단과 겹치지 않게), 최대 폭 560 px. 구성: 투어 이름 · 진행 `n / N` (진행바) · 단계 제목 · 본문 · `이전` · `다음` (마지막 단계는 `완료`) · `×` (종료).
- **375** — 좌우 여백 8 px 전폭 바텀시트, 타임바 위, 최대 높이 40 vh (넘치면 본문 스크롤). 접기 버튼 → 1줄 칩 (`2/6 · 일식 ▴`) 으로 장면 확보. 접힘은 단계가 바뀌어도 유지.
- 교육 모드에서 숨길 것: 관찰 카드 (이미 observe 전용 — 변경 0) · `SatelliteZoomTooltip` (카드와 같은 하단 중앙 — 375 실측 스크린샷에서 겹침 위치).
- **목록 ↔ 단계는 같은 카드 컨테이너의 두 보기** (§교차검증 합의 8) — 투어 없음 = 목록 보기 (`role="list"` 의 항목마다 버튼 1개 · Tab 이동 · Enter/Space 시작), 투어 중 = 단계 보기. 같은 `role="region"` 이 유지되므로 보기 전환 때 포커스 위치 계약 (E7) 이 한 컴포넌트 안에서 닫힌다.
- §3.3 의 레터박스 · 포인터 하이라이트 · 용어 hover 툴팁 · 챕터 네비는 **v1 비-범위** (§비-범위). 「시네마틱 바」 는 위 카드로 대체한다.
- **375 상단 바** (1-E) — Q5 권고 (a): `max-sm` 에서 모드 전환기를 현재 모드 1개 + 펼침 메뉴 (`aria-expanded` 비모달 팝업 — #1380 `shouldPreserveFocus` 계약에 자동 편입) 로 바꾼다. 좌측 그룹이 293 px 이하로 돌아와야 한다 (DoD E9).

### 키보드 · 접근성 (E7)

- 카드 = `role="region"` + `aria-labelledby` (투어 이름). 비모달 — 포커스 트랩 없음.
- 단계 제목 · 본문 래퍼 `aria-live="polite"` — 단계가 바뀌면 낭독.
- 키는 **포커스가 카드 안에 있을 때만**: `→` 다음 · `←` 이전 · `Esc` 투어 종료 (capture 단계 `preventDefault` — 자유 비행 오발화 차단, 표시 패널 Esc 와 같은 방식). 카드 밖에서는 기존 의미 그대로 (캔버스 화살표 = 회전, `Esc` = 자유 비행 → 이탈 감지로 이어짐).
- 투어 시작 시 포커스 → 카드 (제목 또는 `다음`). 단계 이동 후 포커스는 누른 버튼에 남는다 (마지막 단계에서 `다음`이 `완료` 로 바뀌어도 같은 요소). 종료 시 포커스 → 투어 목록의 그 투어 항목 (목록이 다시 보이므로).
- 터치 타깃 ≥ 32 × 32 CSS px (저장소 최소 24 px 보다 크게 — 카드 1차 조작).
- `navigator.webdriver` 가드 (#737) 는 **적용하지 않는다** — 투어는 자동 표시가 아니라 사용자가 고를 때만 시작한다.

cross-validate 1회 — 외부 검증 모델 Antigravity `agy` (`cross_validate.sh architecture`, 2026-10-21 06:23~06:25 UTC, outcome `applied` · `plan_bypass false`). 입력 = 본 ADR 초판 + 아래 셀프 체크 미통과 4축 명시 질문 + 이탈 감지 질문 1개. 10 분 상한 감시를 걸었고 약 2 분에 끝났다 (#1363 hang 재발 없음).

상태 전이: 결과 통합 직후에는 Provisional 을 유지했고, 사용자 결정 (2026-10-21 — Q1~Q8 전부 권고안) 확정과 함께 **Accepted** 로 전이했다.

### 합의 (본문에 반영)

1. **초기 로드 순서 경합** — `UrlSync` 초기 effect 와 별도 투어 effect 가 같은 축 (`t` · `focus`) 에 명령을 두 번 보낸다. ⇒ 진입점을 `UrlSync` 초기 effect 하나로 묶고 `?tour` 유효 시 개별 키 적용을 건너뛴다 (결정 · URL 절).
2. **미소비 `focusViewRequest` 잔류** — `view` 없는 단계도 `setFocusViewRequest(null)` 을 보낸다 (단계 적용 순서 3). 비용 0 인 방어라 수용. 다만 `sim-canvas` `consumeFocusView` 는 포커스 동기마다 요청을 「어느 쪽이든 비운다」 (`sim-canvas.tsx` 주석) — 잔류가 실제로 생기는 경로는 포커스 동기가 돌지 않는 경우 (같은 천체 · 메시 부재) 로 좁다.
3. **투어 중 사용자가 표시 패널을 누르면 URL 오염** — 종료 복원이 표시 URL 키까지 되돌린다 (시작 · 종료 · 복원 절, DoD E5 보강).
4. **사건 id → JD 해석 중복** — `planTourStep` 이 `plannedState` 를 함께 돌려주고 `detectTourDrift` 는 그것만 본다.
5. **시각 비교 허용 오차** — 이탈 판정에도 DoD E2 와 같은 `1e-6` 일.
6. **명령 묶음 중간 상태의 이탈 오판** — `applying` 판정 보류. 단 동기 여부는 미실측이라 PR1 확인 항목으로 남겼다.
7. **온보딩 모달 경합** — `?tour=` 진입 첫 방문은 자동 표시 생략 (`onboarding-modal.tsx` 의 자동 표시 조건 = `!navigator.webdriver && !dismissed` 확인).
8. **목록 보기 ↔ 단계 보기 구조 미명시** — 같은 카드 컨테이너의 두 보기로 명시.
9. **T2-5 「사건 앞뒤 3시간」 을 표현할 필드 부재** — `time: { eventId, offsetHours? }` 추가 (하드코딩 JD 회피).

### 이견 수용

1. **재생 단계의 과소 판정** — 원안: 「`timeScale ≠ 0` 단계는 `timeScale` 변경만 본다」. 외부 모델 반례: T2-5 재생 중 스크러버로 10 년 뒤로 가도 배속이 같으면 이탈이 아니다 — 일식이 없는 장면을 보면서 「돌아가기」 가 안 뜬다. ⇒ 시각을 지정한 재생 단계는 `window` 를 두고 그 밖이면 이탈. 같은 필드가 「자동 정지 없음 (E2) 이면 T4-4 는 언제 끝나나」 라는 지적도 닫는다 — `window` 끝에서 정지 (진행 아님).
2. **PR1 범위 과대** — 원안: 375 모드 전환기 재배치를 PR1 에 포함. 외부 모델 근거: 모드 전환기는 관찰 · 연구 공통 레이아웃이고 #1380 포커스 보존 계약에 닿아 회귀 성격이 투어 엔진과 다르다. ⇒ PR0 으로 분리 (Q8 권고 변경).

### Claude 재분석으로 기각한 외부 모델 제안

1. **「`CameraController` 가 노출되지 않아 테스트가 animatable 0 을 읽을 수 없다」** — 사실과 다르다. dev 빌드 전역 `window.__solarScene` → `meshes.get('sun').getScene().activeCamera` 로 읽힌다 (본 ADR 1-C 실측 스크립트가 바로 그 방법으로 `getAllAnimatablesByTarget(camera)` 를 표본했다). 권고의 나머지 절반 — store 단언은 즉시, 카메라 단언만 정착 대기 — 는 수용해 DoD 머리말을 고쳤다.
2. **「재생 단계에서 일시정지 후 원래 배속으로 돌리면 비이탈로 복귀 — 현행 유지 권고」** — 결론 (현행 유지) 은 같으나 근거가 바뀌었다: 이견 수용 1 의 `window` 가 들어간 뒤로는 정지 동안 흐르지 않은 시각이 `window` 안에 있는 한 비이탈이 맞고, 밖이면 이탈이다. 별도 조치 없음.

### 고유 발견 (Claude — 외부 모델 미지적)

1. **같은 천체 단계는 카메라를 다시 잡지 않는다** (정적 판독) — `sim-canvas` 포커스 동기가 `selectedBodyId` 변화에만 반응한다. 재구도가 필요한 전이는 `view` 를 둬야 한다 → 결정 · 엔진 절에 계약으로 박제. 후속 이슈 불요 (투어 데이터 규칙으로 닫힘).
2. **표시 토글 set 이 장면 준비 전이면 no-op** — `disabledReason(null)` 이 막는다. 초기 단계 적용은 `displayCapabilities !== null` 대기 (URL 절). 선후 실측은 PR1.

후속 이슈 분리 0 건 — 전부 PR0~PR3 범위 안에서 닫힌다.

### A1-1. 반증 — 개요 단계의 시점 각이 진입 경로에 따라 갈린다

T1 의 개요 단계 (1 · 7) 는 `resetCamera` 로 태양 중심에 돌아온다. 그런데 개요 복귀 (`sim-canvas` `syncFocusToScene(null)` → `CameraController.reset(35)`) 는 target 과 거리만 애니메이션하고 **alpha · beta 를 지정하지 않는다**. target tween 이 Babylon `setTarget` (`rebuildAnglesAndRadius`) 을 거쳐 카메라 위치를 고정한 채 각을 다시 셈하므로, 화면의 각은 직전 카메라 위치 (= 진입 경로) 가 정한다 (PR #1396 리뷰 실측). 원래 단계 형식은 개요의 시점 각을 지정할 수 없었다 (`view` 는 천체 포커스 전용 · `facing-parent` 1종). 그래서 같은 단계가 진입 경로마다 다른 화면이 된다.

실측은 실 GPU 1280 × 800, PR2 초안 (develop `830325d0` + T1 · T4 데이터) 에서 했다. beta 는 장면 +Y 에서 잰 각이다. 장면의 황도면은 X–Y 평면이다 (지구 공전 위치 3점의 법선 = ±Z 실측). 황도 북극은 −Z 다 (#1366 `S_z` — 데이터 +Z → 장면 −Z). 그래서 카메라의 황도 고도각은 `asin(|sin α · sin β|)` 로 alpha 에도 의존한다. 표의 102.6° 경로는 alpha ≈ −14.9° 라 고도가 약 14.5° 다 — 황도면을 거의 옆에서 본다 (beta 하나만으로는 고도가 정해지지 않는다 — 예: (α −90°, β 90°) 는 고도 90°). 변경 후에는 세 경로 모두 alpha −90.0° · beta 72.0° (고도 72°) 다.

| 진입 경로 | 개요 단계 beta (변경 전) | 변경 후 |
| --- | --- | --- |
| 처음부터 「다음」 1→7 (2회) | 1단계 72.0° · **7단계 102.6° / 102.4°** — 화성 29.8° · 목성 160° · 토성 94.9~97.9° 포커스를 거치며 바뀐다 | 1~7단계 전부 72.0° (2회) |

| 일식 투어 완료 직후 T1 1단계 | **48.5°** | 72.0° |

102.6° 에서는 궤도가 화면 세로선으로 겹쳐, 7단계가 보이려던 「안쪽 행성일수록 빨리 돈다」 장면이 서지 않는다 (PR2 의 사용자 육안 검토 자료에 스크린샷이 있다). ⇒ **§Concrete Prediction PR2 「새 코드 0 — 데이터 파일만」 은 반증됐다.** 단계 형식이 부족하다는 신호이며, 이 예측이 드러내려던 바로 그 경우다 (`data-not-code-extension` 교훈).

### A1-3. 확장 형식 — 절대 방향 시점 1종

시점을 **상대 시점** (대상 천체가 있어야 방향이 정해진다 — `facing-parent` · PR3 `from-sun`) 과 **절대 시점** (대상과 무관한 고정 방향) 으로 나눈다. 절대 시점은 대상이 없는 개요에도 쓸 수 있다.

### A2-6. 측정 방법 (계약 1 · 2)

실 GPU headful Chromium (`renderer · webgpu`), dev 전역 `window.__solarScene` 으로 장면을 읽는다. 카메라 정착 (animatable 0) 뒤에 잰다.

- **사이각** — `acos((지구 − 카메라)̂ · (지구 − 태양)̂)`. 세 위치 모두 같은 장면 좌표 (Floating Origin 이후 절대 위치 `getAbsolutePosition`) 다.
- **원반 중심 위도** — 지구 메시 world 행렬로 local `+Y` 를 world 로 옮긴 것이 실제 북극이다 (#1362 — 지구만 local `+Y` = 실제 북극). 원반 중심은 지구 → 카메라 방향이므로 위도 = `asin((카메라 − 지구)̂ · 북극)`. 같은 식에 태양 방향을 넣은 태양 직하 위도와 비교했고, 세 단계 모두 소수 3자리까지 같다.
- **북극의 화면 위치** — 북극 방향을 카메라 view 행렬로 옮긴 성분 `(x, y)` 의 `atan2(x, y)` (0° = 화면 위). 또 `Vector3.Project` 로 「중심 + R·북극」 과 중심을 화면에 투영해 y 를 비교했다 (북극 y < 중심 y 면 위쪽 절반).
- 분점의 0 이 아닌 위도 (3월 춘분 프로토타입 −0.15° · 9월 추분 +0.154°) 는 J2000 고정 극 근사 (#1362 §A13.6 — 세차 무시) 와 장면 궤도 모델 잔차다. 3월 실측을 역산하면 장면 태양 황경이 0° 에서 약 0.377° 어긋난다 (`asin(sin(−0.15°) / sin ε)`). 이는 지점의 δ (0.384° · 0.389°) 와 같은 크기다.
