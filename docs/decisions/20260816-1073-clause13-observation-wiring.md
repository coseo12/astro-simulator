## §1 배경 — 조건은 신설됐고 실행 주체가 없다

PR [#1069](https://github.com/coseo12/astro-simulator/pull/1069) ([#1035](https://github.com/coseo12/astro-simulator/issues/1035)) 가 [20260807-971](20260807-971-required-status-checks.md) §10-5 에 **항 13** 을 신설했다. 술어·관측 창·임계가 기계 판정 가능한 형태로 박제됐고, 관측 시점도 _"릴리스 사이클 종료 직후 `O(1)`"_ 로 적혔다.

**적히지 않은 것은 «누가 그것을 돌리는가» 다.** dev 가 반환 보고에서 스스로 인정했고 reviewer 가 재확인했다.

이 저장소는 같은 사슬이 **두 번** 끊긴 이력이 있다:

| 세대 | 위임 | 수신처 상태 | 결과 |
| --- | --- | --- | --- |
| 1 | [#962](https://github.com/coseo12/astro-simulator/issues/962) 축 B 후속 F1 | 표에만 존재 (이슈 미생성) | [#970](https://github.com/coseo12/astro-simulator/issues/970) 으로 **재발견** |
| 2 | [#1014](https://github.com/coseo12/astro-simulator/issues/1014) → 971 §재검토 조건 | 착지점 **0항** | [#1035](https://github.com/coseo12/astro-simulator/issues/1035) 로 **재발견** |
| 3 | 항 13 → _"매 사이클 관측"_ | **실행 주체 부재** | 본 ADR 이 닫는다 |

세대 2 가 고친 것은 «조건이 존재하는가» 이고, 세대 3 이 남긴 것은 «조건이 발화하는가» 다. 조건문은 있는데 그 조건을 평가하는 주체가 없으면 **결과는 조건이 없는 것과 동일**하다.

## §2 선행 조건 실측 — 차단 2건은 해소됐다

이슈는 _"술어가 확정되기 전에 배선하면 잘못된 술어를 제도화한다"_ 를 선행 조건으로 걸었다. #1069 는 머지돼 v0.74.0 에 포함됐으나, **해소 여부는 develop 본문으로 재확인해야 한다.** 아래는 전부 `develop` tip `d0b5b5e` 에서 2026-08-16 실행한 결과다 (`gh` GET 전용 / `jq`).

### 2-1 측정 1 — 항 13 (0) 술어의 판별력 (양성·음성 대조군 동시)

박제된 (0) 경로를 **문자 그대로 추출해** 7 PR 에 돌렸다. `escape = 0` 주장이 _"없다"_ 인지 _"술어가 어긋났다"_ 인지 구분하려면 같은 실행에 양성이 있어야 한다.

| PR | 클래스 | `mergedAt` | 판정 | 기대 |
| --- | --- | --- | --- | --- |
| `#636` | `base=main` | `2026-06-08T15:24:16Z` | **ESCAPE** | 양성 (소급 기준선) |
| `#646` | `base=main` | `2026-06-10T07:30:22Z` | **ESCAPE** | 양성 |
| `#652` | `base=main` | `2026-06-10T13:24:37Z` | **ESCAPE** | 양성 |
| `#658` | `base=main` | `2026-06-10T17:13:38Z` | **ESCAPE** | 양성 |
| `#1067` | `head=release/0.73.0-prep` | `2026-08-14T03:47:04Z` | clean | 음성 |
| `#1068` | `base=main` | `2026-08-14T04:02:14Z` | clean | 음성 |
| `#1088` | `base=main` | `2026-08-15T18:23:38Z` | clean | 음성 |

**양성 `4/4` · 음성 `3/3`.** 술어는 살아 있고 판별력이 있다.

### 2-2 측정 2 — 🔴-1 (`--limit` 절단) 해소, fail-fast 로

현행 항 13 은 `LIMIT=1000` + **포화 assertion** (`반환 건수 == LIMIT` 이면 `exit 1`) 을 갖는다. **negative 실증**을 같은 스크립트로 확인했다:

| 실행 | 반환 건수 | 결과 |
| --- | --- | --- |
| `LIMIT=1000` | `628` | `[assert] 비포화 (628 < 1000)` → 진행, `escape = 0` |
| `LIMIT=300` | `300` | `FAIL: --limit 300 포화 — 창 절단. LIMIT 를 올려 재실행` · **exit `1`** |

이슈가 지적한 _"조용한 절단"_ 은 **더 이상 조용하지 않다.** 절단은 여전히 일어나지만 `exit 1` 로 드러난다 — 이것이 [guard-design-principles.md](../lessons/guard-design-principles.md) §3 이 요구하는 fail-fast 형태다 (fallback 분기 없음).

### 2-3 측정 3 — 🔴-2 (T1 조치의 자기 소거) 해소, 주입 대조로

현행 항 13 은 **머지 시점 앵커** (`started_at <= mergedAt`) 를 쓴다. 앵커가 실제로 T1 조치 (b)(_"사후 정정해 재발화"_)를 무력화하는지 확인하려면 **사후 정정 run 이 실재해야 하는데 실측 보유 PR 은 `0`건**이다. 그래서 실 escape PR (`#636`) 의 `check-runs` 응답에 **사후 정정 run 1건을 주입**해 2×2 로 갈랐다.

주입 값: `{name: "pr-template-checklist", conclusion: "success", started_at: "2026-06-09T15:24:16Z"}` (= `mergedAt + 1일`).

| | 무앵커 술어 (`success = 0 ∧ failure >= 1`) | **앵커 술어 (채택)** |
| --- | --- | --- |
| **대조군** (주입 없음) | `s=0 f=1` → ESCAPE | `s=0 f=1` → ESCAPE |
| **처리군** (사후 정정 주입 = T1 (b) 시뮬레이션) | `s=1 f=1` → **clean** (자기 소거 발생) | `s=0 f=1` → **ESCAPE** (면역) |

**갈림은 정확히 한 셀 (처리군 × 무앵커) 에서만 발생한다.** 초판 술어였다면 T1 (b) 를 수행하는 순간 그 PR 이 계수에서 사라져 `escape >= 2` 가 원리적으로 성립 불가능했고, 앵커는 그것을 구조적으로 막는다.

> ⚠️ **첫 실행은 무효였고 정정 후 재실행했다.** BSD `date` 에서 `-v+1d` 를 `-f <fmt> <date>` **뒤에** 두면 오프셋과 출력 포맷이 함께 무시돼 `Mon Jun 8 15:24:16 UTC 2026` 이 나온다. 그 문자열로도 결론은 같았으나 (jq 문자열 비교에서 `"M" > "2"` 라 우연히 배제됨) **판정 이유가 앵커가 아니라 포맷 사고**였다. `-v` 를 `-f` 앞으로 옮기고 `[0-9][0-9][0-9][0-9]-*Z` 형태 assertion 을 붙여 재실행한 것이 위 표다. 이 저장소의 «재현 술어 오류» 클래스([#1064](https://github.com/coseo12/astro-simulator/issues/1064) §측정 6-1) 를 본 ADR 이 작성 중에 한 번 재생산했다는 기록으로 남긴다.

### 2-4 측정 4 — 실효 창의 현재 상태

`SINCE = max(2026-08-14T00:00:00Z, now-90d) = 2026-08-14T00:00:00Z`. 릴리스 클래스 모집단 **`4`** (`#1067` `#1068` `#1087` `#1088`), **`escape = 0`**.

**⇒ 차단 2건은 해소됐다. 술어 교정이 아니라 배선이 다음 단계다.** (단 §3-2 가 별건의 정합성 결함 1건을 새로 찾았다.)

## §3 실측 — 배선 설계의 입력

### 3-1 측정 5 — 관측 트리거 빈도: _"O(1)"_ 은 1회 비용이지 총 부담이 아니다

항 13 은 관측 시점을 _"릴리스 사이클 종료 직후 `O(1)`"_ 로만 적었고 **빈도를 적지 않았다.** 실측하면 그 침묵이 결정을 바꾼다.

| 창 | release PR (`base=main`) 머지 | 릴리스 클래스 전건 |
| --- | --- | --- |
| 최근 30일 | **`26`** (`0.87` 회/일) | **`52`** (`1.73` 회/일) |
| 최근 60일 | `48` | `96` |
| 최근 90일 | `60` | `118` |

부수 확인 — 태그 `v*` **`79`개** (`2026-04-14` ~ `2026-08-16`), `base=main` 머지 PR 전 기간 **`156`건**.

**⇒ 관측은 «가끔 있는 의례» 가 아니라 «하루 1~2회 반복 작업» 이다.** 1회 비용이 `O(1)` 인 것과, 그것을 사람이 월 26회 빠짐없이 수행하는 것은 다른 명제다.

### 3-2 측정 6 — **신규 발견**: (0) 경로가 모집단의 진부분집합이다

항 13 안에서 두 서술이 어긋난다:

- **모집단 (1)** 필터 — `baseRefName == "main"` **∨** `headRefName` 이 `release/` 로 시작
- **관측 시점 (0)** 서술 — _"release PR 머지 직후 그 PR **1건**만 판정한다"_

릴리스 1사이클은 PR **2건**이다 (실측: `#1087` `base=develop` `head=release/0.74.0-prep` → `#1088` `base=main` `head=develop`). (0) 을 release PR 에만 돌리면 **prep PR 이 관측에서 통째로 빠진다.**

| 릴리스 클래스 하위 분해 (전 기간) | 계수 |
| --- | --- |
| 합계 | `214` |
| release PR (`base=main`) | `156` |
| prep PR (`head=release/*`) | **`65`** |
| 교집합 (둘 다 참) | `7` |

**갭이 이론이 아닌 이유** — [`operational-friction.md`](../ops/operational-friction.md) §릴리스 부수 마찰 이 박제한 _"첫 run `failure` 3건이 전부 prep PR"_ (`#912` `#964` `#1032`) 이 그 클래스다. 다만 셋 다 (0) 술어로는 **`clean`** 이다 (머지 전에 정정됐다). 그리고 소급 기준선 escape `4/4` 는 **전부 `base=main`** 이라 **현재 갈림은 `0`** 이다.

**⇒ 위험은 미발현이나 방향이 거짓 음성이다.** §2-2·2-3 이 닫은 두 결함과 정확히 같은 클래스(_"틀릴 때 escape 를 놓치는 쪽으로만 틀린다"_)이므로, 배선하면서 함께 닫는다 (§결정 4).

### 3-3 측정 7 — 저장소의 자동화 전례

| 형태 | 계수 | 비고 |
| --- | --- | --- |
| `schedule:` 보유 workflow | **`0`** | cron 전례 없음 |
| `cron` 문자열 보유 workflow | **`0`** | 위와 독립 확인 |
| `workflow_dispatch:` 보유 (양성 대조군) | `5` | grep 이 동작함을 실증 |
| `types: [closed]` 보유 (양성 대조군) | `1` | `auto-close-issues.yml` |

**⇒ cron 은 전례가 없고 필요도 없다.** 관측 시점이 «릴리스 사이클 종료» 라는 **이벤트**이므로 `auto-close-issues.yml` ([#915](https://github.com/coseo12/astro-simulator/issues/915)) 의 `pull_request: types: [closed]` 구조가 그대로 맞는다 — 그 workflow 는 `permissions: issues: write` + `contents: read` 로 이미 «머지 이벤트를 받아 이슈를 조작하는» 전례를 만들었다.

## §4 후보 비교

### 4-1 축 1 — 관측 실행 주체

| 후보 | 실행 증거가 남는가 | 월 26~52회 부담 | 판정 |
| --- | --- | --- | --- |
| **(a) 사람 규약** (릴리스 절차 명시 스텝) | **아니오** — 미실행과 `clean` 이 구별 불가 | 사람 | 기각 (주) |
| **(b) 이벤트 구동 workflow** | **예** — run 이력 | 기계 | **채택** |
| (c) cron workflow | 예 | 기계 | 기각 — 트리거가 시각이 아니라 이벤트다. 창 경계와 릴리스 시점이 어긋나 latency 만 늘린다. 전례도 `0` (§3-3) |
| (d) 기각 (관측 미발생 명시) | 해당 없음 | `0` | 기각 — §4-4 |

**(a) 기각의 결정적 근거는 부담이 아니라 «증거 부재» 다.** 항 13 자신이 ⚠️ 로 경고한 것이 _"이 술어는 거짓 음성 방향으로만 틀리므로 조용한 실패가 곧 «escape 없음» 으로 읽힌다"_ 인데, 사람 규약은 **그 실패 모드를 술어 밖에서 한 번 더 재생산**한다 — 관측이 스킵돼도 산출물이 `escape = 0` 과 구별되지 않는다. workflow 는 run 이력이라는 **독립 증거**를 만들어 «미실행» 과 «`clean`» 을 분리한다.

보강 실측 — [#1064](https://github.com/coseo12/astro-simulator/issues/1064) ADR §결정 6 이 박제한 경고가 같은 방향이다: _"[20260808-983](20260808-983-measurement-recording-convention.md) §(ii)·(iv) 는 발화 지점이 `0` 이며 주의력에만 의존한다. PR #1061 은 그 상태에서 **4라운드 연속** 수치 오류를 냈다."_ 월 1회짜리 규약도 그랬는데 월 26회는 더 나을 이유가 없다.

### 4-3 축 3 — 주기: 릴리스 절차의 명시적 스텝으로 올릴 것인가

**올리지 않는다.** 근거 2항:

1. **부담 실측** (§3-1) — 명시적 사람 스텝은 월 26~52회다. 스텝을 늘리면 §4-1 (a) 를 기각한 이유가 그대로 재현된다.
2. **관측 지연의 비용이 낮다는 실측** — `check-runs` 는 GitHub 에 영구 보존되므로 **90일 창 안에서는 (1)+(2) 전수 재산출이 언제든 같은 답을 낸다.** 즉 «매 사이클» 은 **데이터 보존 요구가 아니라 latency 요구**다. 실제로 §2 의 측정 1·4 는 사후에 실행해 소급 4건을 전건 재현했다. 예외는 T1 (a) 대장의 _"당시 본문 형태"_ 필드 하나뿐인데, 그것은 T1 (b) 를 수행하기 전까지 보존된다.

⇒ 기계가 매 사이클 돌고(latency 최소), 사람은 **창 이탈 전 fallback 1회**만 진다.

### 4-4 축 4 — 기각안 (_"항 13 은 조건만 존재하고 관측은 발생하지 않는다"_)

**기각한다.** 실측 근거 — 현 체제 base rate 는 `0 / 63일` 이고 실효 창 escape 도 `0` 이라 _"관측을 안 해도 당장 손해가 없다"_ 는 참이다. 그러나 그것은 **관측을 안 해도 되는 근거가 아니라 관측 비용이 싸다는 근거**다 (기계 1회 실행 = GET 2회). 관측을 포기하면 항 13 의 T1·T2 가 전부 도달 불가능해져 [#1069](https://github.com/coseo12/astro-simulator/pull/1069) 가 한 작업 전체가 무효가 된다.

⚠️ **그럼에도 이 후보를 표에 남기는 이유**는 이슈 본문 4항이 요구한 것이 _"기각도 결론"_ 이기 때문이다. 침묵 기각이 이 이슈가 생긴 원인 그 자체이므로, 기각안도 **후보로 비교된 뒤 근거와 함께 기각**됐음을 여기 박제한다.

### 결정 2 — [20260814-1031-1064](20260814-1031-1064-committed-claim-guard-rejected.md) §결정 6 과 **정합한다** (개정 불요)

§결정 6 의 문언은 _"박제된 **감시값**과 **실측**의 **대조** 주체는 사람이다. 기계는 **관측값 출력까지만** 담당한다"_ 이다. 본 결정은 그 경계를 **그대로 지킨다** — 기계는 `ESCAPE`/`clean` 을 출력할 뿐이고, 그 뒤의 모든 행동(대장 원인 분류 / 사후 정정 / 재개봉)은 사람이다.

**두 건이 다른 클래스라는 것이 더 중요하다:**

| | #1064 축 B (기각됨) | 항 13 (본 배선) |
| --- | --- | --- |
| 술어 소재 | 산문 안에 흩어짐 | ADR 본문의 **실행 가능한 코드 블록** |
| rev 결속 | 자연어 anaphora — 기계가 잇지 못함 (§측정 3-1) | **없음** — 항상 현재 API 상태 |
| 파라미터 | 추출 대상이 불특정 | **PR 번호 1개** |
| 판정 형태 | 박제 «숫자» 대비 대조 → 의미론 판정 | **자기완결 술어** — `s`/`f` 계수 → 임계 비교 |
| 실행 안전성 | 동기가 된 술어 자신이 allowlist 통과 불가 (§측정 4) | `gh` **GET 2회** |
| 정밀도 실측 | `0/17`, `0/2` | 양성 `4/4` · 음성 `3/3` (§2-1) |

⇒ §결정 6 이 기각한 것은 _"산문 술어를 기계가 추출·재실행하게 만드는 일"_ 이지 _"기계가 관측을 실행하는 일"_ 이 아니다. **ADR 개정은 동반되지 않는다.**

### 결정 3 — workflow 사양 (구현 계약)

```yaml
on:
  pull_request:
    types: [closed]
```

- **`branches:` 필터 미사용** — 모집단 조건이 `base == main` **∨** `head` 가 `release/` 로 시작이라 `branches:` (base 축 단독) 로 **표현 불가능**하다. job `if:` 로 판정한다.
- **job `if:`** — `merged == true` **∧** (`base.ref == 'main'` **∨** `startsWith(head.ref, 'release/')`). 이 술어는 항 13 모집단 (1) 필터와 **동형이며 사본이 아니라 같은 조건의 이벤트 표현**이다.
- **`permissions`** — `checks: read` · `contents: read` · `issues: write` (`auto-close-issues.yml` 최소 권한 관례 승계). `-X PUT/PATCH/DELETE` 로 저장소 설정을 만지지 않는다.
- **`concurrency` 미채택** — 971 **결정 9-2** 계승 (동명 축 증식 회피).
- **저장소 보호 설정 무접촉** — 971 §결정 1 required 3개 · §결정 9-1 · Phase 1 면제 근거 **전부 무접촉**. 본 workflow 는 `closed` 이벤트라 머지 게이트에 원리적으로 개입할 수 없다.
- **출력 계약** — `ESCAPE` 이면 `[ADR Trigger]` 이슈 생성 + job **실패**. `clean` 이면 job summary 에 판정 1줄 기록 후 성공. 어느 쪽이든 **run 이력이 남는 것이 본 설계의 핵심 산출물**이다.
- **fail-fast** — 항 13 의 두 assertion(포화 / 조회 실패)을 그대로 승계한다. fallback 분기 · `|| true` · soft-exit **금지** ([guard-design-principles.md](../lessons/guard-design-principles.md) §3).

### 결정 4 — 관측 대상을 **그 사이클의 릴리스 클래스 머지 PR 전건**으로 정정한다 (§3-2 갭)

항 13 (0) 의 _"release PR 머지 직후 그 PR 1건"_ 서술을 **모집단 (1) 과 정합하도록** 교정한다. prep PR 도 트리거된다 (결정 3 의 `if:` 가 이미 그 형태다). 판정 비용은 PR 당 `O(1)` 로 불변이고, 사이클당 실행 횟수가 `1 → 2` 로 는다.

근거는 §3-2 — 현재 갈림은 `0` 이나 방향이 거짓 음성이고, `pr-template-checklist` 첫 run `failure` 의 실측 밀도는 prep PR 쪽이 낮지 않다.

### 결정 5 — 배선 위치: 971 항 13 이 정본, `operational-friction.md` 는 **포인터 1줄**

- **971 §10-5 항 13** 에 «관측 주체» 서브블록 신설 — **실행 주체 · 주기 · 실패 시 조치 3항**을 한 곳에 둔다 (이슈 완료 기준).
- **`operational-friction.md` §릴리스 부수 마찰** — workflow 이름 + 발화 시 행동 + 971 링크. **임계값·창·술어 복제 `0`**.
- **CLAUDE.md · `branch-strategy-workflow.md` 무접촉** (§4-2).

### 결정 6 — 실패 시 조치 (3분기, 명시)

| 실패 형태 | 조치 |
| --- | --- |
| **관측 결과가 `ESCAPE`** | T1: **(a) 먼저** 971 §escape 대장에 박제 → **(b) 그 다음** 본문 사후 정정. `escape >= 2` 도달 시 T2 = 결정 9-1 **재개봉** (편입 승인 아님) |

### 결정 7 — 항 14 는 본 배선 범위 **밖** (침묵하지 않고 분리)

항 14 (base 편집 escape) 는 **같은 «관측 주체 공백» 클래스이나 배선 형태가 다르다**:

| | 항 13 | 항 14 |
| --- | --- | --- |
| 술어 정본 | 971 항 13 | [20260814-1027](20260814-1027-pr-base-edit-guard.md) **§9-2 조건 1** |

| 트리거 | 릴리스 사이클 종료 (이벤트 존재) | base 편집 (`0 / 110일` — 이벤트 희소) |

## §6 결과 · 재검토 조건

### 결과

- **코드 수정 `0`** (본 ADR PR). workflow 구현은 후속 (§8 후속 1) — 본 PR 은 **문서만**이며 `.github/workflows/` 무접촉.

- **[20260814-1031-1064](20260814-1031-1064-committed-claim-guard-rejected.md) 무접촉** — §결정 2 가 정합을 확인했으므로 개정 불요.

### Concrete Prediction

- **971 §10-5 에 «관측 가능한 재검토 조건» 이 추가로 신설될 때**: `release-escape-watch.yml` 변경 **`0` 줄**이면 예측 성공 — 단 **조건이 항 13 과 같은 3속성** (트리거가 릴리스 사이클 이벤트 · 비용 `O(1)` · 판정이 자기완결 술어) 을 가질 때만이다.
  - 검증: 그 신설 PR 에서 `git diff --stat .github/workflows/release-escape-watch.yml`
  - 실패 시 대응: 3속성 중 어느 것이 깨졌는지 먼저 판정한다. 항 14 처럼 **속성이 다르면 예측 실패가 아니라 적용 범위 밖**이다 (§결정 7). 속성이 같은데도 변경이 필요했다면 workflow 에 조항별 지식이 샌 것이므로 **리팩토링 후 재개**.

### 재검토 조건

1. **workflow 가 `ESCAPE` 를 1회라도 출력** → 결정 6 의 T1 경로. 동시에 본 ADR §4-4 의 _"base rate `0`"_ 전제가 깨지므로 관측 주기(§4-3)를 재검토한다.
2. **workflow 미발화가 실측으로 발견** (릴리스 클래스 머지 PR 대비 관측 run 수 부족) → **`1`건이라도** 본 결정을 재검토한다. 이것은 본 설계가 사람 규약에서 물려받지 **않았다고 주장한** 실패 모드이므로, 첫 반례의 정보량이 가장 크다. 관측 술어:
   ```bash
   # 창 안의 릴리스 클래스 머지 PR 수 ↔ release-escape-watch 성공 run 수 대조 (GET 전용)
   gh run list --repo coseo12/astro-simulator --workflow release-escape-watch.yml \
     --limit 200 --json databaseId,conclusion,event | jq 'length'
   ```
   ⚠️ 두 수가 같아야 한다는 뜻이 **아니다** — 재실행·취소가 있으므로 **PR 번호 집합의 포함 관계**로 본다. 판정 주체는 사람이다 (§결정 2 와 같은 계급).
3. **workflow job 실패가 `2` 사이클 연속** → 자동화의 유지비가 사람 규약 부담(§3-1)을 넘어선 것이므로 §4-1 을 다시 연다.
4. **관측 트리거 빈도가 `<= 2회/30일` 로 하락** (§3-1 의 `26` 에서 한 자릿수로) → 자동화 근거의 주축이 약해진다. 사람 규약(§4-1 (a))을 재검토하되, «증거 부재» 논거는 빈도와 **독립**이므로 그것만으로는 뒤집히지 않는다.
5. **`pr-template-checklist` 가 required 로 편입** (T2 재개봉의 결과로) → escape 가 **구조적으로 불가능**해지므로 본 배선 전체가 불요해진다. 그때 workflow 를 제거하고 항 13 을 Superseded 처리한다.
6. **trigger 가 아닌 것 (명시)** — _"오래 `clean` 만 나온다"_ 는 재검토 트리거가 **아니다**. 그것이 본 조항이 감시하는 사건의 base rate 가 `0` 이라는 뜻이며, [#1064](https://github.com/coseo12/astro-simulator/issues/1064) ADR §재검토 조건 5 와 같은 정렬이다.

## §9 교차검증 반영 사항

⚠️ **미수행 — 본 ADR 은 `Provisional` 이다.** cross-validate 는 메인이 수행한다 ([#479](https://github.com/coseo12/astro-simulator/issues/479) — sub-agent 직접 호출 금지). 수행 후 본 절에 **합의 / 이견 수용 / Claude 재분석으로 기각 / 고유 발견** 4축을 통합하고 `Accepted` 전이 + `README.md` 인덱스 상태 열을 **같은 커밋**에서 갱신한다 ([#1005](https://github.com/coseo12/astro-simulator/issues/1005) 가 강제).

### 호출 전 Claude 편향 셀프 체크 ([cross-validate-protocol.md](../guides/cross-validate-protocol.md) §5)

| 축 | 통과 | 비고 |
| --- | --- | --- |
| 낙관적 일정 | ❌ **미통과** | _"`auto-close-issues.yml` 구조를 그대로 쓰면 된다"_ 로 구현 난도를 낮게 잡았을 수 있다. 실제 위험은 `if:` 표현식(`startsWith` + `merged`)의 Actions 평가 시점과 `gh` 인증 컨텍스트다 — 둘 다 **미실측**. 완화로 §8 후속 1 에 DoD 4축을 못박았으나 셀프 체크는 미통과로 남긴다 |
| 결합 간과 | ✅ 통과 | 971 결정 1·9-1·9-2 / 1064 §결정 6 / 1027 §9-2 / 항 14 결합을 전건 검토했고, §3-2 에서 항 13 **내부**의 정합성 결함을 새로 찾았다 |
| 폐기 프레이밍 | ⚠️ **부분** | 사람 규약을 «기각» 이 아니라 «fallback 으로 강등» (§결정 6 3행) 으로 남겼으나, §4-3 이 명시적 절차 스텝화를 거부한 것은 사람 축을 약화시키는 방향이다. 근거를 빈도 실측(§3-1)에 고정했다 |
| 순수주의 | ✅ 통과 | 사본 `0` 원칙을 §4-2 (b) 에서 완화해 운영 문서에 포인터 1줄을 허용했다 |

**호출 프롬프트 삽입 질문 (미통과·부분 축)**:

1. `pull_request: types: [closed]` + `if: merged && (base.ref == 'main' || startsWith(head.ref, 'release/'))` 조합이 fork PR · 봇 PR · base 편집 후 머지에서 의도대로 평가되는가. 평가되지 않는 조합이 있다면 그것은 거짓 음성인가 거짓 양성인가.
2. 관측을 기계로 옮기면 «사람이 아무도 안 본다» 는 새 실패 모드가 생기는가. §재검토 조건 2 의 술어가 그것을 잡기에 충분한가.
3. 사람 규약(§4-1 (a))을 fallback 으로만 남긴 것이 과소평가인가 — 월 26회 부담 실측이 그 판정을 지지하는가.
